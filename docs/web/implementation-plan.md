# 実装計画

ステータス: **承認待ち**（最終更新: 2026-11-06）

設計は [architecture.md](architecture.md)。この計画は、設計の承認後に着手する。

## 1. 並行して開発するための方針

- **土台（フェーズ0）だけは1人で順番に作る**。ここで型・DB スキーマ・部品の置き場所・規約を固め、以降の作業がぶつからないようにする。
- **契約を先に決める**：domain の関数の型（シグネチャ）と、service の関数の型をフェーズ0で書いておき、中身は空（`throw new Error('not implemented')`）にする。画面の担当者は型を見て作り始め、仮のデータで表示を確認できる。
- **担当の範囲（ディレクトリ）を分ける**：レーンごとに触るディレクトリを決めて、競合を減らす（下の表）。
- 1タスク＝1ブランチ（git worktree）＝1PR。PR ではテストと型チェックが通ることを必須にする。

## 2. 全体像（依存関係）

```
フェーズ0  土台（直列）
  0-1 プロジェクト作成 → 0-2 DB・認証 → 0-3 型と契約 ┐
                       └→ 0-4 トークン・部品の基盤 ──┤
                                                    ▼
フェーズ1  並行（4レーン）
  A domain ロジック   ─────────────────┐
  B UI 部品           ─────────────────┤
  C server（repository・service・actions）┤
  D アプリの外枠（ログイン・レイアウト・PWA）┘
                                                    ▼
フェーズ2  画面（並行、ただし①が先）
  ①記録 ─┬→ ⑧量の記録 ─┐
         ├→ ④⑤習慣の管理 ┤
         └→ ⑥振り返り → ②③ ┤
                                                    ▼
フェーズ3  仕上げ（並行）
  オンボーディング・空の状態 ／ ⑦設定・アカウント ／ E2E
                                                    ▼
フェーズ4  通知・公開準備
```

## 3. フェーズ0：土台（直列・1人）

| # | タスク | 内容 | 完了の条件 |
|---|---|---|---|
| 0-1 | プロジェクト作成 | Next.js ＋ TypeScript（strict）＋ pnpm、ESLint・Prettier、Vitest、Tailwind v4、ディレクトリ構成（architecture.md 2章）、`docker compose`（Postgres） | `pnpm dev` / `pnpm test` / `pnpm lint` が動く |
| 0-2 | DB・認証 | Drizzle のスキーマ（全テーブル）とマイグレーション、Auth.js（Google）、`requireUser()`、middleware、初回ログイン時の `user_settings` の作成 | Google でログインし、保護されたページが表示できる |
| 0-3 | 型と契約 | `domain/types.ts`、domain の各関数と service の各関数のシグネチャ（中身は空）、テスト用データの作成関数（fixture） | 型チェックが通る。各レーンが参照できる |
| 0-4 | トークン・部品の基盤 | `tokens.css`（tokens.json から生成）、フォント、PC のスマホ幅固定レイアウト、部品のカタログページ `/dev/components` | カタログページにトークンの見本が出る |

> 0-4 は 0-2 と並行してもよい（触るファイルが別）。担当が2人いれば 0-1 のあとに分ける。

外部の準備（ユーザー側の作業。0-2 までに必要）：
- Google Cloud で OAuth クライアントを作る（ローカル用のリダイレクト URL）
- GitHub のリモートを作る
- （フェーズ2の終わりまでに）Vercel と Neon のアカウント

## 4. フェーズ1：基盤の中身（並行・4レーン）

| レーン | 触るディレクトリ | タスク | 依存 |
|---|---|---|---|
| **A domain** | `src/domain/` | A1 論理日付・週・月の範囲（`date.ts`）<br>A2 達成判定・進み具合（`achievement.ts`）<br>A3 連続記録（`streak.ts`）<br>A4 草のレベル（`grass.ts`）<br>A5 振り返りの文章（`review.ts`）<br>A6 セリフの選択とセリフのデータ（`grumble.ts`） | A1 → A2 → A3 → A5。A4・A6 は A2 のあと並行 |
| **B UI 部品** | `src/components/` | B1 基本：`Pill` `Tag` `Marker` `ScreenHeader` `SegmentTabs` `TabBar`<br>B2 記録：`CheckBox` `ProgressBar` `WeekDots` `HabitRow` `SummaryCard` `Toast`<br>B3 キャラ：SVG の書き出し、`Mascot`（4表情・2形態）`Speech`<br>B4 草：`GrassHeatmap` `CalendarModal` `StatBox`<br>B5 シート：`BottomSheet` `NumPad` `QuantityTotalSheet` `QuantityIncrementSheet`<br>B6 `EmptyState`、フォーム部品（周期・記録方式の選択、数値の±） | B1 が先。B2〜B6 は並行 |
| **C server** | `src/server/` | C1 repository（habits / entries / settings）＋統合テストの環境<br>C2 記録の service と actions（チェック、量の合計・1回分の追加・削除、1日1行の保証、取り消し）<br>C3 習慣の service と actions（追加・編集・過去にする・戻す・並び順）<br>C4 振り返りの service（期間の記録をまとめて取得 → domain で計算） | C1 → C2・C3 は並行。C4 は C1 のあと（domain A2〜A5 の中身ができたら結合） |
| **D 外枠** | `src/app/(auth)`、`(main)/layout`、`manifest`、SW | D1 ログイン画面（B1 のデザイン）<br>D2 `(main)` のレイアウト（下部タブ）、オンボーディング前の振り分け<br>D3 PWA（Manifest、アイコン、Serwist、オフライン時の表示） | D1・D2 は B1 のあと。D3 は独立 |

- 各タスクの完了の条件：A はユニットテスト（境界条件を含む）、B はカタログページで Figma と見比べて確認、C は統合テスト、D は実際に動く画面。

## 5. フェーズ2：画面（並行、①が先）

| # | 画面 | 依存 | 完了の条件 |
|---|---|---|---|
| 2-1 | **①-a/b/c 記録**（楽観的更新、＋の長押しと取り消しトースト、セリフ） | A2・A6、B2・B3、C2、D2 | 今日・今週・今月の記録ができ、集計とセリフが変わる |
| 2-2 | ⑧-a/b 量の記録のシート | 2-1、B5、C2 | 合計の入力と1回分の追加ができる |
| 2-3 | ④ 一覧、⑤-a 追加、⑤-b 編集 | B1・B6、C3、D2 | 習慣の追加・編集・過去にする・戻すができる |
| 2-4 | ⑥-a 振り返り、⑥-b 日付を選ぶ | A3〜A5、B4、C4 | 年間の草と文章が表示され、日付を選べる |

## 8. 人数ごとの進め方の目安

| 人数（エージェント数） | 進め方 |
|---|---|
| 1 | フェーズ0 → A・C を交互 → B → 画面の順 |
| 2 | フェーズ0 のあと「A＋C（ロジックとサーバー）」と「B＋D（見た目と外枠）」に分ける。フェーズ2 は「①⑧②」と「④⑤⑥③」 |
| 4 | フェーズ1 を4レーンで。フェーズ2 は 2-1 ／ 2-3 ／ 2-4 → 2-5 ／ B の残り → 2-6 |

並行で作業する人数が多いほど、フェーズ0-3（型と契約）の重要度が上がる。契約を変えるときは、変更する PR を先にマージしてから各レーンに取り込む。
